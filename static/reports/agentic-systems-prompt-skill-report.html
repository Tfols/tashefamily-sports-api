§0Introduction: Two Layers, One Stack

"Agentic skills" and "agent prompting" are often discussed as one topic, but they are really two distinct design problems stacked on top of each other. This report treats them separately, in the order an agent actually depends on them, before drawing out the discipline that turns out to govern both.

The prompt layer is the moment-to-moment substrate: the system instructions, tool/function specifications, in-context examples, and output-format rules an agent reasons from on every single turn, with or without any packaged capability loaded. It exists for every agent, always.

The skill layer sits on top of it: a portable, filesystem-based package — conventionally a folder containing a SKILL.md file plus optional scripts, references, and assets — that bundles reusable procedural knowledge so an agent does not need the same workflow re-explained every session. Skills are only as reliable as the prompt-layer design underneath them; a well-packaged skill built on ambiguous tool descriptions will still fail.

A methodological note before the substance: the material below is drawn from a mix of vendor engineering documentation, official guides, peer-reviewed and pre-print academic literature, and community-maintained resources. Where a claim rests on a single 2026 preprint rather than a replicated or peer-reviewed finding, this report says so explicitly, consistent with treating exact effect sizes as illustrative of scale rather than settled constants. The closing section collects these caveats in one place alongside the full source list.

Part IThe Skill Layer

1.1What a Skill Is

The packaging format — a folder with a required SKILL.md file (YAML frontmatter plus markdown instructions) and optional scripts/, references/, and assets/ subfolders — originated at a single vendor but has since been published as an open, independently governed specification (agentskills.io), adopted across a wide range of agent products including coding assistants, IDE integrations, and enterprise platforms. Because it is now a shared, cross-platform specification rather than a proprietary format, the design principles in this section are genuinely portable rather than tied to one company's implementation.

The architecture every implementation of the standard shares is progressive disclosure, structured in three tiers:

  • Tier 1 — Discovery. At startup, an agent loads only each skill's name and description: just enough to judge relevance without paying a context cost for content it may never use.
  • Tier 2 — Activation. When a task appears to match, the agent reads the full SKILL.md body into context.
  • Tier 3 — Reference. Only if the task genuinely requires it does the agent open bundled reference files or execute bundled scripts.

This is the load-bearing design decision in the entire system: it is what lets an agent have access to dozens of skills without every one of them consuming context space it is not currently using.

1.2Writing the Skill Prompt: What the Evidence Says Matters Most

The description field carries almost the entire burden of whether a skill is used at all. Because it is the only text loaded before a triggering decision is made, an under-specified description means the skill silently never fires when it should, while an over-broad one fires when it shouldn't and wastes context. The open standard's own authoring guidance frames this explicitly as a precision/recall problem: the recommended practice is to build a small validation set of prompts that should and should not trigger the skill, then iteratively revise the description against that set and track a pass rate — treating description-writing as something tested, not written once and trusted.

A 2026 academic treatment of this same problem (a paper on trigger precision for LLM-authored skills, published as a preprint) formalizes it further, extracting explicit positive and negative trigger phrases from a skill's description and representing them with context-aware embeddings, because the same phrase can legitimately belong in both an activation and an exclusion context depending on framing. The practical takeaway, independent of the formal machinery: ambiguous wording in a description is not just imprecise, it is actively confusable with its opposite — so being explicit about exclusions ("use this for X, not for Y") is doing real work, not just being thorough.

Inside the body of the instructions, the recurring advice across the open specification's documentation and vendor guides built on it converges on a small set of points:

  • Numbered, procedural steps rather than explanatory prose — agents follow sequences more reliably than they extract procedures from paragraphs.
  • Concrete templates and worked examples rather than descriptions of desired output — pattern-matching against an exact example is more reliable than inferring a format from a description of it.
  • Explicit edge cases and explicit statements of what to skip and why, rather than leaving boundary conditions to inference.
  • Keeping the main file lean and pushing infrequently needed material into separate reference files — a widely circulated community heuristic (not part of the formal specification itself) suggests that if a piece of information is needed in under roughly a fifth of invocations, it belongs in a reference file.
  • Being unambiguous about whether bundled code is meant to be executed (a script the agent runs, with only the output entering context) or read as reference documentation — leaving this implicit is a common source of an agent wasting context reading source code it should have simply run.

1.3The Layer Underneath: Tool and Prompt Design

Skills typically wrap or coordinate tools, so tool-design quality directly limits skill reliability. The most comprehensive vendor-neutral treatment here is OpenAI's "A Practical Guide to Building Agents," which distills patterns across many production deployments rather than a single house style. Its central claim, echoed widely elsewhere: high-quality instructions are the single biggest success factor for an agent — it is only as reliable as the instructions and tool descriptions it is given.

Concrete, recurring recommendations from that guide and adjacent production experience:

  • Convert existing standard operating procedures directly into prompt steps rather than writing instructions from scratch — translating an already-working human process faithfully outperforms improvising a new one.
  • Use prompt templates with variables rather than duplicating near-identical full prompts across scenarios, for both maintainability and consistency.
  • Watch for tool overload as a signal to split responsibilities across multiple agents. The issue is not strictly the number of tools but their similarity or overlap — some deployments manage more than 15 well-defined, distinct tools successfully, while others struggle with fewer than 10 that overlap in function. The fix-order matters: try improving tool clarity (better names, parameters, descriptions) first; only split into multiple agents if that fails to resolve the confusion.
  • When splitting is warranted, two orchestration patterns are broadly validated: a manager pattern (a central agent calls specialized agents as tools and synthesizes results) suited to tasks needing unified synthesis, and a decentralized / handoff pattern (agents transfer control to one another directly) suited to triage-style workflows where no single agent needs to retain oversight.
  • Build evaluations early against the most capable available model to establish a real accuracy ceiling before economizing with a smaller one — otherwise it is impossible to tell whether a smaller model is failing the task or the task was never verified as achievable in the first place.

1.4The Evaluation and Iteration Loop

Skill quality is treated, across the available guidance, as something produced by observation rather than upfront perfection. The recurring loop: start with evaluation — run the agent on representative tasks and see where it struggles before writing anything; build skills incrementally to close specific, observed gaps; watch how the agent actually navigates the skill in practice, including unexpected trajectories or overreliance on particular bundled files; and iterate directly with the agent, asking it to reflect on what went wrong when a task fails and to help capture what worked when it succeeds.

This mirrors broader agent-evaluation guidance: teams often delay building evaluations because they assume hundreds of test cases are needed, when in practice 20–50 tasks drawn from real observed failures is a solid starting point, since early-stage effect sizes are usually large enough that small samples reveal problems clearly.

1.5Empirical Evidence: Does It Actually Help?

⬡ KEY FINDING

A controlled academic evaluation (OpenSkillEval, testing over 600 dynamically generated tasks against 30 community-sourced skills across five real-world application categories) found that skill availability does not guarantee effective skill usage, that the benefit of skill augmentation depends strongly on both the underlying model and the agent framework, and that many publicly popular skills do not reliably outperform the base agent without the skill at all. It further found that for tasks whose core difficulty is reasoning and analytical judgment — as opposed to procedural formatting or workflow sequencing — existing skills provided only limited benefit.

OpenSkillEval, 2026 · 600+ tasks, 30 skills

The practical implication: a skill's value should be measured, not assumed. If a skill targets a fundamentally reasoning-heavy problem rather than a workflow-execution problem, the procedural-skill format is unlikely to move the needle much — that is a case for better prompting or a stronger model, not more procedural scaffolding.

1.6Robustness as an Adversarial Property

"Robust" in this space increasingly means "resistant to manipulation," not just "reliably triggers and executes correctly." A 2026 security paper studying real skills pulled from a public registry demonstrated that natural-language skill metadata is itself an attack surface at three distinct points in a skill's lifecycle:

  • Discovery. Short textual triggers appended to a SKILL.md file can manipulate embedding-based retrieval and improve an adversarial skill's visibility in a registry.
  • Selection. Description-only framing can bias an agent toward selecting a functionally deceptive variant over a legitimate one.
  • Governance. Semantic evasion strategies can let malicious instructions avoid triggering a safety-blocking verdict from automated scanners.

In the paper's own framing, a SKILL.md file is not passive documentation but operational text that shapes which third-party capabilities an agent finds, trusts, and uses. A related systematization-of-knowledge paper on the same threat surface categorizes this as "poisoned skill retrieval," explicitly analogizing it to SEO poisoning in web search — the retrieval mechanism can be gamed with the same techniques that game any embedding-based ranking system. A separate benchmarking paper proposes scoring skills on an "Instruction Fidelity Risk" scale, where the highest-severity case is a skill that incorporates unsanitized user- or web-supplied free text directly into agent instructions without any scoping or sanitization.

⚠ RISK — SKILL METADATA AS ATTACK SURFACE

Practical implications for anyone authoring or installing skills: treat any skill not personally authored, and not fully read, as untrusted — this applies to the SKILL.md text itself, not just bundled scripts. Be skeptical of skills whose description makes capability claims that are hard to verify against what the bundled code and instructions actually do — documented "false-advertisement" attacks are exactly this mismatch. Any skill accepting free-text input and feeding it into agent instructions or tool parameters without sanitization is the highest-risk configuration by design.

1.7Skill Registries and Directories

The ecosystem for discovering and installing skills has grown quickly enough to include several distinct categories, each with a different risk profile:

  • The specification itself — hosted openly on GitHub (agentskills/agentskills) — is the canonical reference for what a valid SKILL.md package looks like, not a database of skills.
  • Vendor-bundled collections — official first-party skill repositories maintained directly by specific platforms — carry essentially zero supply-chain risk since they are published directly by the platform, at the cost of narrow selection.
  • Curated cross-platform directories (e.g., skills.sh, maintained by Vercel) market themselves specifically as a higher-quality-bar alternative to the fully open community pool.
  • Fully open community registries (e.g., ClawHub) are currently the largest pools — reported at over 13,000 published skills as of early 2026 — and also the source of a documented, serious security incident (see below).
  • Large aggregator directories (e.g., SkillsMP) index skills across multiple source registries for discoverability, meaning their quality signal is only as good as the registries they pull from.
  • Self-hosted enterprise registries (e.g., the open-source SkillHub project) offer private, access-controlled, audited internal distribution — arguably the more defensible model for organizational use beyond personal experimentation.
⚠ INCIDENT — "CLAWHAVOC"

A coordinated campaign planted several hundred malicious skills in a fully open community registry using typosquatted names — subtle misspellings of trusted skill names — that distributed credential-stealing malware and exfiltrated SSH keys, API tokens, and browser session cookies from installs. A separate third-party audit reportedly flagged roughly 13% of scanned skills for critical security issues, including prompt injection risks and exposed API keys. The registry has since added automated malware scanning and removed thousands of suspicious listings, but this should be read as a live, reactive fix rather than a solved problem.

Overall assessment: this ecosystem currently resembles an early, imperfectly policed app store more than a mature package registry — comparable to where early extension or package ecosystems stood before mature vetting emerged, security incidents included. Preferring official or heavily curated sources over the raw open pool, and actually reading a skill's SKILL.md and any bundled scripts before installing, is not optional caution given the above — it is the baseline given what has already happened in this specific ecosystem.

1.8Examples of "Good" in the Skill Layer

The clearest examples of good skill-authoring guidance are not finished skills to imitate wholesale, but documented methodologies for building and testing them:

  • Description-optimization workflow (agentskills.io). The open specification's own authoring guide documents a concrete testing loop: generate a set of prompts that should and should not trigger a given skill, run them against the current description, measure a pass rate, revise the description to close gaps in precision or recall, and repeat — a directly reusable process independent of any specific skill's content.
  • Skill-creation tooling patterns. Several skill-authoring tools in the ecosystem implement a structured build loop — interview the intended use case, draft the skill, run it against baseline (no-skill) and prior-iteration comparisons, grade outputs (sometimes via an independent "grader" agent to reduce author bias), and iterate — which is a good template for anyone building a custom skill rather than installing one.

What counts as "good" here is best understood as a property of the process that produced a skill (was it tested against real triggering ambiguity, was it evaluated against a no-skill baseline, was its description precision-tuned) rather than a property that can be judged by reading a finished SKILL.md file in isolation.

Part IIThe Prompt Layer

2.1What the Prompt Layer Covers

Four distinct things get bundled under this term, and they have different failure modes:

  • System-level instructions — the standing behavioral guidance an agent operates under.
  • In-context examples (few-shot demonstrations) — showing rather than telling.
  • Tool / function specifications — the schemas and descriptions defining what actions an agent can take and how.
  • Output structuring — how the shape of a response is constrained (JSON, specific formats, etc.).

2.2Foundational Techniques

A small number of techniques are close to consensus because they have been replicated extensively. Few-shot prompting — showing input/output examples rather than only describing a task — was formally characterized in the original GPT-3 paper (Brown et al., 2020) and remains one of the most reliable levers for steering output toward a specific format or style. Chain-of-thought prompting — inducing step-by-step reasoning before a final answer — was shown (Wei et al., 2022) to substantially improve multi-step reasoning performance and remains one of the most consistently replicated findings in the literature.

Beyond these two, the field has produced a large taxonomy of techniques with varying evidentiary support. The most comprehensive attempt to organize this is a 2024 systematic survey (Schulhoff et al., "The Prompt Report"), which catalogued 58 distinct LLM prompting techniques and 33 vocabulary terms through a formal PRISMA-style review of more than 1,500 papers — arguably the closest thing this field has to a settled taxonomy rather than competing vendor terminology. One finding from that project worth flagging on its own: automated prompt-optimization methods were able to outperform the paper's own human prompt engineer on the tasks tested — evidence that systematic search over prompt variants can beat expert intuition, even expert intuition.

2.3Prompt Brittleness: The Central Empirical Finding

⬡ KEY FINDING

A substantial and consistent body of research documents prompt brittleness (also called format sensitivity): models can produce meaningfully different outputs from prompts that are semantically identical but differ in superficial, non-meaningful ways — spacing, delimiter choice, or example ordering.

  • Sclar et al. (2024) showed that changing only the formatting of a prompt — delimiter choice, minor spacing differences, content held constant — produced performance swings of up to 76 points on a benchmark suite of instruction-following tasks. That is not a marginal effect; it exceeds the performance gap between many models.
  • Zhao et al. (2021) found that the specific choice and ordering of few-shot examples could shift GPT-3's classification accuracy by up to 30%, and proposed a calibration method to partially correct for it — one of the earliest and most cited papers establishing that few-shot examples are a source of instability if not controlled for, not simply a free improvement.
  • Lu et al. (2022) systematically studied the effect of example order specifically, finding that permutations of the same example set could swing accuracy substantially, and — importantly — that the best-performing order did not reliably transfer from one model to another. There is no universal "correct order" to memorize; it is model- and task-specific.
  • Bertsch et al. (2024) found that order-sensitivity meaningfully decreases when models are given very long context with hundreds of demonstrations rather than a handful, suggesting the issue is partly about limited context inducing overweighting of position cues — and that longer-context models may be somewhat more forgiving, though this does not eliminate the problem.

The practical implication is a genuine reframe: there is no such thing as verifying a prompt is good by reading it and judging that it sounds clear. A prompt that reads as unambiguous can still be unstable under formatting variation that happens naturally across sessions, API versions, or minor edits. The only defense the literature converges on is empirical testing across variants — generating multiple phrasings or formats of the same instruction and measuring output consistency, rather than trusting a single hand-tuned version. This is the same "test, don't assume" discipline that governs skill-description triggering (§1.2), and it is, if anything, more load-bearing at the raw prompt layer, since no packaging structure catches ambiguity the way progressive disclosure does for skills.

2.4Tool and Function Specification Design

Tool and function specifications are prompts too — natural-language (or natural-language-adjacent, via JSON schema descriptions) text loaded into context and interpreted, subject to the same instability concerns above. The pattern that converges across most production guidance, independent of vendor, is to treat a tool definition the way one would write onboarding documentation for a new employee: make implicit context explicit (specialized formats, internal terminology, relationships between resources), avoid ambiguous parameter names, and provide concrete examples of correctly formatted calls rather than relying on a schema alone to convey usage. Production guidance converges on a related, distinct point: when an agent starts making tool-selection errors, the first fix is improving tool clarity — better names, tighter parameter definitions, more explicit descriptions — and only if that fails should responsibilities be split across multiple agents; treating tool confusion as an orchestration problem before ruling out a specification problem is a common, avoidable source of premature complexity.

2.5Adversarial Robustness

If "robust" is meant in the security sense rather than the reliability sense, this is the least mature and most consequential area. Indirect prompt injection — malicious instructions embedded in content an agent retrieves or processes (a webpage, a document, a tool's output) rather than typed directly by a user — is a well-established, actively studied attack class against tool-using agents specifically, because an agent that reads external content and then acts on tools is structurally exposed to that content in a way a plain chatbot is not.

The most credible empirical grounding is AgentDojo (Debenedetti et al., NeurIPS 2024), a benchmark built specifically to evaluate prompt injection attacks and defenses against realistic tool-using agents (email management, banking-style tasks). Its findings are directly relevant to prompt design:

  • Simple, prompt-level defenses measurably help: wrapping tool outputs in explicit delimiters with instructions to treat enclosed content as data rather than instructions; "prompt sandwiching," repeating the original user instructions again after a tool call returns (to counteract the tendency for the most recently seen instructions — possibly injected — to dominate); and restricting the agent to only the tools plausibly needed for a task before it observes any untrusted data, so a compromised tool result cannot unlock unnecessary tool access.
⚠ KEY FINDING — NO COMPLETE DEFENSE

None of the tested defenses are close to a complete solution. Across the defenses evaluated in the AgentDojo benchmark, essentially all of them cost roughly 15–20% of task utility specifically when under active attack — there is a real trade-off between injection robustness and full capability, not a free win. A 2025 follow-up (PromptArmor), using a separate guardrail LLM specifically prompted to screen for injected content, reports substantially better figures — sub-1% false-positive and false-negative rates on the same benchmark — suggesting the frontier has moved, though this is a single paper's result on one benchmark, not yet a settled finding.

A broader 2025 survey of agentic security makes a structural point worth internalizing: the safety training a base model receives does not reliably transfer into the agentic context, and the static, predictable structure of a typical system prompt is itself identified as a vulnerability that injection attacks exploit — a system prompt that is boilerplate and guessable is easier to attack around than one with less predictable structure.

2.6Examples of "Good" in the Prompt Layer

Two genuinely different categories of example are worth distinguishing here.

A. Intentionally published, pedagogical examples

OpenAI's own prompting guides, published in its Cookbook as worked, annotated examples rather than abstract advice — particularly the GPT-4.1 and GPT-5 / GPT-5.1 guides — are the strongest examples available of the craft, not just advice about it:

  • They present a concrete recommended prompt skeleton — role/objective, instructions with sub-categories, explicit reasoning steps, output format, worked examples, then a final instruction — while explicitly inviting deviation rather than treating it as rigid.
  • They document why a specific change worked, with a number attached: adding three explicit sentences instructing a model to persist until a task is genuinely resolved, to gather information itself rather than guess, and to plan explicitly before tool calls produced close to a 20% improvement on a coding benchmark — a concrete demonstration that small, well-placed prompt text can matter enormously, directly consistent with the brittleness research in §2.3.
  • They incorporate externally validated findings, not just vendor claims: Cursor's engineering team found that wrapping instruction categories in structured XML-style tags (e.g., <persistence>, <context_understanding>) improved instruction adherence and allowed cross-referencing sections elsewhere in the prompt.

A separate cookbook entry, "Building Resilient Prompts Using an Evaluation Flywheel," is a good example of a different kind of write-up — not a template, but a documented methodology for diagnosing and iteratively fixing a brittle prompt: reading a sample of failing outputs, applying descriptive labels to what is going wrong (open coding), grouping those into higher-level failure categories (axial coding), and only then building automated graders around the categories that actually matter. This is essentially the "test, don't assume" discipline from §2.3 turned into a repeatable process.

B. Real production system prompts (third-party extracted)

A small ecosystem of actively maintained repositories collects system prompts extracted from major commercial AI products, organized by vendor and version, with the largest reportedly exceeding 130,000 GitHub stars and covering 30-plus tools including versioned tool-calling schemas, not just prose instructions. These are genuinely valuable for studying real, battle-tested structural choices at scale — for instance, a documented second-generation rewrite of one product's agent prompt, or the specific XML-tag conventions different products converge on independently.

Important caveats: these are unofficial extractions (typically via adversarial prompting or other extraction techniques), not vendor-endorsed exemplars — inclusion in a collection does not mean the content represents recommended best practice, and some of it likely reflects messy, accumulated, real-world compromises rather than clean design. These prompts also go stale quickly as vendors iterate, and there are legitimate legal and ethical questions around scraping and republishing another company's proprietary configuration. They are best treated as material for pattern study — the way one would study a competitor's public-facing product — rather than as source text to copy from directly.

§3Cross-Cutting Synthesis

Pulling both layers together, a small number of principles recur regardless of which layer is being designed:

01

Measurement beats intuition, at every level.

Whether the object being judged is a raw system prompt, a tool description, or a skill's triggering description, the same finding holds: a human reading it and judging it clear is not evidence that it behaves reliably. Small, seemingly cosmetic changes — formatting, ordering, phrasing — can produce large behavioral swings. The only practices with real evidentiary support are empirical: build a small test set (20–50 real cases is enough to start), test variants against it, and revise based on observed failures.

02

Clarity for a human reader is necessary but not sufficient.

Writing for "a new hire" — explicit context, unambiguous naming, concrete examples — is good practice at every layer, but it does not by itself guarantee robustness to formatting variation or adversarial manipulation. Both require separate, additional defenses.

03

Neither layer is a solved problem, especially on security.

Indirect prompt injection at the tool-use layer and metadata manipulation at the skill-registry layer are both active, unresolved research areas as of mid-2026, with defenses that measurably trade away capability rather than eliminating the risk. Any deployment that processes untrusted external content through a tool-using agent should be built with this trade-off in mind, not treated as a hypothetical.

04

Complexity should be earned, not defaulted to.

Both layers show the same anti-pattern: reaching for more architecture (more agents, more tools, more elaborate skill scaffolding) before exhausting simpler fixes (clearer tool descriptions, a better-tuned skill description, a more explicit prompt). The evidence consistently favors fixing specification clarity first.

§4Source Quality and Epistemic Notes

In keeping with treating sourcing rigor as part of the deliverable, not an afterthought, this section states plainly what kind of evidence underlies each part of this report.

Vendor engineering documentation and official guides (the open Agent Skills specification, OpenAI's agent-building and prompting guides) reflect production experience at scale and are treated as reliable practitioner guidance, though they are not independently peer-reviewed and naturally emphasize each publisher's own tooling.

Peer-reviewed or well-established academic work (the original few-shot and chain-of-thought papers, the Prompt Report survey, AgentDojo) is treated as the strongest tier of evidence in this report, subject to the normal caveat that any single benchmark or study captures a specific experimental setting.

2026 preprints (OpenSkillEval, the SKILL.md supply-chain security paper, the agentic-skills systematization-of-knowledge paper, the skill trigger-precision paper, PromptArmor, the agentic security survey) have not necessarily completed formal peer review, and in a fast-moving area like this, findings can be superseded quickly. This report treats their qualitative conclusions — skills do not automatically help; skill and prompt metadata are exploitable attack surfaces; injection defenses trade away utility — as well-supported, since they are consistent across multiple independent sources. Specific quantitative figures from single preprints (e.g., an 86% win rate, a 77.6% selection rate, a 76-point swing) are held more loosely, as snapshots under specific experimental conditions rather than durable constants.

Community and journalistic sources (registry statistics, security-incident reporting, curated "best-of" lists) are used only for factual, verifiable claims (star counts, incident descriptions, registry size) and are flagged as such; they are not used as evidence for design-best-practice claims.

A small number of well-known foundational results (Brown et al. 2020 on few-shot learning; Wei et al. 2022 on chain-of-thought) are cited as established background rather than freshly retrieved and verified in this research session; they are included because they are extremely well replicated and widely known, not because they were directly re-examined here.
